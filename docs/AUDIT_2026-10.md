# JARVIS MCU — Bug & Gap Audit (2026-10)

> Status: **advisory.** This is a point-in-time review of the kernel/MCU migration
> against its own roadmap and Constitution. It records findings and
> recommendations; it changes no behaviour. Fixes are deliberately **not** bundled
> here — each becomes its own staged release if adopted.

## 1. Scope & method

- **Audited at:** `main` @ 8.212.0 (Phase AE enforce merged; commit `d78ccff`).
- **Read:** `docs/KERNEL_PLAN.md` (1199 lines), `docs/JARVIS_CONSTITUTION.md`,
  `KERNEL_ADOPTION.md`, `scripts/kernel_adoption.py` (`_DECLARED`), the six kernel
  CI gates, the phase/task tracker, and spot-checks of the code behind the claims
  (`actuation.py`, `cognitive_core.py`, `agent.py`, `identity.py`, `continuity.py`,
  `kernel/certification.py`).
- **Method:** compare the *declared* adoption stage of each kernel primitive and
  the roadmap's phase status against what the code actually enforces at runtime;
  run all six kernel gates + `audit.py`; enumerate the live unit-test failures in
  this container and root-cause them.
- **Not in scope:** a line-by-line security review of every actuator path (the
  bypass/coverage gates already assert the structural invariant); feature design.

### 2a. Pure primitives with no live owner — "staged-ahead" code (GAP)

Eight primitives are `pure` with `owners=[]` and **no live caller**: `coordination`,
`household`, `inquiry`, `priority`, `privacy`, `resilience`, `social`, `surfaces`.
(`persistence` is the ninth pure entry but is a *by-design* seam consumed by other
kernel modules, not live callers — not dead weight.)

Each was built ahead of the roadmap phase that would consume it (household→P,
social/privacy→W, resilience→Z, surfaces→AA, coordination→AB, priority→AC,
inquiry→AD — all **pending**). That is defensible under the plan's "wrap, don't
rebuild" premise *only if those phases are actually coming*; today they are inert
code that inflates the kernel surface and the adoption matrix without exercising
anything. **Risk:** a reader of the matrix can mistake "declared, tested pure" for
"adopted." **Recommendation:** either sequence the consuming phase or annotate
these rows explicitly as *staged-ahead, no consumer yet* so the ladder stays
honest. (Low urgency — they are harmless, just not load-bearing.)

### 2b. Primitives parked at shadow/parity — genuine seams vs. stalled (watch)

The 14 shadow + 6 parity primitives are observe-only or compared-not-authoritative.
Most are genuine seams with a live caller and a named enforce path (e.g.
`outcome`, `router`, `beliefs`, `attention`, `uncertainty`, `plan`,
`long_horizon`). Two are wired only at package level (`event_bus`, `ledger` →
`__init__`) and never advanced — acceptable as infrastructure, but they will sit
at shadow forever by nature, so their stage is not a progress signal. No action
required; flagged so the matrix isn't read as "20 primitives mid-migration" when
several are terminal-by-design.

## 3. Roadmap vs. reality — gaps

- **Stale Progress table (GAP, doc).** `docs/KERNEL_PLAN.md` lines ~13–28 still show
  Phases **4–7 as "🚧 In progress"** with last release `8.12.0`, and say "🚧 marks
  phases whose remaining work is wiring consumers to enforce." Reality at 8.212.0:
  authority, causal → **enforce**; plan → parity; beliefs/attention/router →
  shadow. The table has not been advanced in ~200 releases. It contradicts the
  live adoption matrix and should either be regenerated from `_DECLARED` or deleted
  in favour of `KERNEL_ADOPTION.md` as the single source of truth.
- **Pending roadmap phases:** I, P, S, T, V, W, Z, AA, AB, AC, AD remain pending.
  Several have kernel substrate already pure/shadow (I→agency_state shadow;
  S→self_model parity; T→graph enforce + beliefs/uncertainty; V→long_horizon
  parity; P/W/Z/AA/AB/AC/AD→the pure primitives in §2a). So the substrate exists;
  the *authoritative dependence* does not. This matches the plan's own thesis
  ("consolidation, not features") — the open work is wiring, not building.
- **Done-bars reached:** Kernel Foundation (H) ✅, Cognitive/Agency Architecture
  (R) ✅, MCU System (AE) ✅ *for the observable set* (see §4). The three bars in
  `KERNEL_PLAN.md §"Definitions of done"` are internally consistent with the code.

## 5. Governance / invariant weaknesses

- **"More intelligence never means less governance" (#68) holds structurally.** The
  bypass gate (32 service calls converge-or-classified), coverage gate (every
  consequential agent tool declared actuator/read-only), and authority/budget/
  loop_detect enforce flips are the teeth. `audit.py` + six kernel gates are green.
- **Blind spot — CI-time, not runtime.** All governance gates are *static* (they
  assert code structure at build). A live home can still neutralise a flip via
  config (every enforce reads a `*_enforce` config key); that is intended
  (owner-gated kill-switches), but it means the Constitution's claims describe
  *available* governance, not *active* governance in a given deployment. Worth one
  sentence in the Constitution so "enforce" is not read as "always on".
- **No runtime assertion that a disabled governance flip is logged.** Flipping an
  enforce off is silent. Low priority, but a one-line "governance flip off" log
  would make an over-permissive home diagnosable.

## 6. Test health — live-home contamination (GAP, test-isolation)

**8 unit tests fail in this container; all pass in clean CI.** Root cause: the
container mounts the owner's live `/config/jarvis/config.json`, which sets
`environment_enforce / identity_fabric_enforce / learning_enforce /
autonomy_enforce / cognitive_cycle_enforce = true` (plus `output_mutes.json`
`all:true`). The affected "off by default" / shadow tests read those same keys
through `jarvis_config` and so see enforce ON:

- `test_actuation_learning_enforce.py::{test_enforce_off_by_default, test_off_persists_nothing}` ← `learning_enforce`
- `test_autonomy_enforce.py::test_enforce_off_by_default` ← `autonomy_enforce`
- `test_energy_environment_enforce.py::{test_enforce_off_by_default, test_default_off_returns_legacy_over_peak}` ← `environment_enforce`
- `test_identity_fabric_enforce.py::test_enforce_off_by_default` ← `identity_fabric_enforce`
- `test_attention_shadow.py::test_can_announce_decisions_unchanged_with_shadow`, `test_delivery_triggers.py::test_concurrent_evaluations_announce_once` ← `output_mutes.json all:true` / live presence state

**Assessment:** this is a real **test-isolation bug**, not a product bug — the unit
suite should not read a developer's live HA config. It masks regressions (a test
that should assert "off by default" silently exercises the ON path) and makes the
in-container suite permanently red, which erodes the "green before merge" signal.
**Recommended follow-up (own PR, not here):** an autouse fixture in
`tests/conftest.py` that points these tests' `jarvis_config` at an empty/temp dir
(or monkeypatches `jarvis_config.get` to the declared defaults) so unit tests are
hermetic regardless of the host's `/config`. Small and safe; est. ½ day.

### Bottom line

The MCU migration is in good structural health: H/R/AE done-bars are met, six CI
gates enforce the governance contract, and no unsafe fail-open was found. The real
debt is **honesty-of-signal and hygiene**, not correctness: a stale roadmap table,
eight kernel primitives staged ahead of any consumer, two AE classes that cannot
yet certify, a weak `security` closure signal, and a unit suite that reads the
host's live config. None blocks Phase Ω; all are worth clearing (or consciously
accepting) before the v9.0.0 bump so the 9.0 line starts from an honest baseline.
